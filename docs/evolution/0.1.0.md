# Public research core 0.1.0

## Problem

The internal Harness combines personal integration and correction research. A public release needs a reusable mechanism and truthful evolution history without exporting personal configuration, runtime state, or actual records. Reusing an internal package number would obscure the narrower public scope.

## Architecture and interface

The public distribution contains an explicit-root HCD event ledger, evidence-aware acceptance state, manual structured pattern clustering, a manual intervention marker, recurrence, and schema 3 reporting. Sessions and project identity must be supplied explicitly. Reports lead with correction-pattern recurrence; ordinal D is secondary. No collector, training runner, automatic maintenance, live publisher, memory server, authentication server, or cloud runtime is included.

## Decisions and alternatives

Extract a bounded standard-library core rather than copying the internal runtime/dependency closure. Reject symlinks and credential-class paths; keep imports free of writes and host discovery. Preserve the event-state and pattern protocol while replacing personal defaults. The public version is 0.1.0; internal package 1.0.0 and MCP interface 1.0.3 remain lineage only. Earlier internal milestones were not public releases of this repository.

Public extraction also fixes a supported-member edge case: repeating one member ID cannot satisfy a pattern's two-distinct-member requirement. Runner fields, member types, and the disabled profile are validated strictly; numeric substitutes for booleans are rejected. These fixes are in the public copy and do not claim a deployment to the private system.

## Research hypotheses

Separating first direction, plan/result acceptance, and later correction may prevent stale success judgments. Shared cross-task causes and post-intervention recurrence may be useful investigation units. Provisional student labels may reduce classification cost, but their agreement with model clustering is not user-verified accuracy. These are research hypotheses; passing a state-machine test is not evidence of causal benefit.

## Validation and limits

Synthetic TaskA/TaskB tests exercise idempotency, immutable anchors, acceptance invalidation, expiry, explicit identity, secret-like input rejection, symlink rejection, pattern support, cross-task recurrence, label disagreement, and disabled integration profiles. A deterministic demo marks an intervention and reproduces recurrence without models or production inputs. Public boundary tests enforce the declared payload. Linux CI specifies supported Python versions; local verification does not preclaim that remote CI has already run.

Actual task coverage and real-user benefit remain unknown. Weak acceptance and first-pass rates are observational proxies. The filesystem checks are a library guard, not an OS sandbox. All actual records, even anonymized ones, are excluded from release payloads.

## Next

Expand falsifiable event-order and ownership counterexamples; compare clustering strategies on predeclared synthetic holdouts; keep model adapters separate until their dependency and resource boundaries are reviewable. Maintain architecture, evolution, changelog, version, and payload checks with every public update. [Engram](https://github.com/Ming-Sir-69/engram) continues as a separate knowledge project; this core's role remains correction evaluation.
